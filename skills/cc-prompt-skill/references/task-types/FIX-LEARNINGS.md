# FIX Task -- Accumulated Session Learnings

Session learnings from FIX task executions (+).

**Usage:**
- **COO reads this** when writing FIX prompts; selects 3-5 relevant entries and embeds them in the prompt's §8 IMPORTANT NOTES.
- **CC does NOT load this file at runtime** -- curated learnings arrive in the prompt, not via reference read.
- **Size discipline:** if this file exceeds ~20KB, prune entries older than many sessions and archive to `FIX-LEARNINGS-ARCHIVE.md`.

**Rationale:** Splitting CORE (spec + delegation, ~2KB) from LEARNINGS (accumulated history, ~13KB) keeps CC's per-task FIX context load small while preserving the full record for COO authoring.

## Session Learnings

**Workflow FIX notes:**
- Multi-trigger VERIFICATION fallback: when a FIX targets a node that runs on the schedule path (e.g., a Postgres detection query), and the workflow has BOTH webhook and schedule triggers, MCP `execute_workflow` fires the webhook path only -- the fixed node will NOT run. Specify safe-sql direct query as the primary verification path in the VERIFICATION section: "Run the updated SQL via safe-sql webhook and verify it returns expected rows." Document the test as PARTIAL ("SQL logic verified; schedule path E2E pending next cron"). See ANTI-PATTERNS #43 and n8n-workflows.md Multi-Trigger Workflows.: VERIFICATION section said "check execution output" but safe-sql was the correct verification path.
- Data flow summary for workflow FIX prompts: include a brief (3-5 line) description of the workflow's execution paths in the CONTEXT section. Format: one line per path (e.g., "SKIP path: Extract Invoice Data -> Is Skip? (port 0) -> Merge / Non-skip path: Parse Body -> Insert -> Update Email Log -> Merge"). Without this, CC spends 10-15 minutes independently reconstructing the flow before it can diagnose cross-path expression failures. This is especially important when the bug involves cross-node references or 0-item propagation across branches.: CC independently discovered the SKIP vs non-skip path split and the Update Email Log 0-item design gap -- a data flow summary would have made these root causes obvious at inspection..
- DoD verification scope: if the fix only addresses one node in a multi-node pipeline, split the DoD into two checks: (1) "fix node returns expected rows/output" and (2) "full pipeline completes successfully." Pre-existing bugs in downstream nodes will block (2) without invalidating (1). Don't write a single checkbox that conflates them — CC will mark it failed even when the targeted fix worked correctly.
- Known pre-existing issues: if prior executions of the target workflow show errors in nodes OTHER than the broken node, list them in an IMPORTANT NOTES sub-section: "Known pre-existing bugs (not in scope): {node} - {error}." This prevents CC from chasing unrelated failures during verification and keeps the fix surgical.
- Error framing: avoid "intermittent" without a root-cause hypothesis. If the underlying bug is deterministic (always fails given condition X), say "consistently failing since [date/event X]." "Intermittent" triggers a timing/race-condition diagnostic approach; "consistently failing since X" triggers a code/config diff approach. Framing affects where CC looks first.
- Metric tracking plumbing: if a FIX adds metric tracking to a health check node (e.g., filtered_count, processed_count), explicitly specify the plumbing mechanism. `$getWorkflowStaticData()` is only available in Code nodes — NOT in n8n Postgres expression context. Options: (a) pass the metric as a field on each output item from the upstream Code node (safe with explicit `queryReplacement` — extra fields ignored), (b) compute in a new Code node before the health check. Specify which to avoid an implementation guess.
- Column name verification: for FIX prompts that modify SQL INSERTs, include exact column list verified via `SELECT column_name FROM information_schema.columns WHERE table_name = '{table}'` (archived — live DB is authoritative). Swapped column VALUES (correct columns, wrong value order) produce type errors Postgres reports as cryptic parse failures — e.g., "Token 'X' is invalid" means a string was put into a jsonb column.
- SSOT-first for inline specs: Never describe DB column specs (types, constraints, defaults) inline in prompts without a verification method. Inline specs go stale — include a live DB query in the ACCESS CHECK or reference `HEALTH-CHECK-PATTERNS.md` as authoritative. If specs are included for convenience, mark: "Verify via live DB before executing." lesson: stale check_id reference from a README caused multiple prompts to spec a non-existent column.
- Field name verification before data flow changes: When a FIX touches data flow across nodes, CC must query the current workflow definition via REST GET and verify field names exist in actual node output before building. Do not rely on prompt field names — always validate against the live workflow. lesson: prompt said `$json._email_id` but actual field was `$json._gmail_id`.
- Explicit lookup strategy for writebacks: When a writeback (e.g., P3 routed_to_table) requires a PK that isn't in the upstream Insert node's output, explicitly state the lookup strategy in the prompt. Options: (a) subquery on a unique field, (b) SELECT after INSERT, (c) add RETURNING clause. If the PK availability is uncertain, say so: "Verify expense_id is in Insert output; if not, use [strategy]." lesson: CC had to invent a subquery mid-build because no strategy was provided.
- Schema facts in CONTEXT go stale: if CONTEXT embeds inline schema column facts (e.g., "check_id: varchar NOT NULL"), add "(verify against live ACCESS CHECK — may be stale from a prior schema version)." CC should always trust the live DB query over the prompt. Best: include a schema query in CC ACCESS CHECK instead of inlining facts (live DB is authoritative, archived — live DB is authoritative).
- Supabase REST DELETE filter column: when writing `?{column}=in.(...)` delete commands, verify the filter column exists in the target table via live DB query. Different tables use different identifier columns -- e.g., `haios_health_checks` uses `component`; `haios_remediation_log` uses `workflow_name` (no `component` column).: prompt specified `?component=in.(...)` for `haios_remediation_log` -- column does not exist, delete would silently return 0 rows. The same rule applies: verify column names before writing any REST filter, not just SQL bodies.
- Cleanup method for test rows: any prompt that creates test rows (e.g., Expense Entry validation) MUST specify deletion via Supabase REST API with service role key -- NEVER via safe-db-write. safe-db-write supports INSERT/UPDATE only on specific tables; it blocks DELETE with an explicit error. Pattern: `DELETE /rest/v1/{table}?{filter_col}=eq.{value}` with `apikey` + `Authorization: Bearer {key}` headers. See the anti-pattern log.: prompt said "delete via safe-db-write" -- blocked; fallback to Supabase REST required.
- safe-db-write UPDATE allowlist for newly-added columns: safe-db-write UPDATE operations check a per-table column allowlist. If a FIX prompt uses ALTER TABLE to add a new column and then UPDATEs that column via safe-db-write in the same task, the UPDATE will fail -- the new column is not yet in the allowlist. Two options: (1) expand the safe-db-write allowlist for that table before the task, or (2) note explicitly in the prompt that the initial UPDATE must use psycopg2 directly (same pattern as ALTER TABLE DDL). If psycopg2 fallback is acceptable for this task, note it: "If safe-db-write UPDATE rejects the new column, fall back to psycopg2.": liveness_window_hours column added via ALTER TABLE, UPDATE via safe-db-write blocked, psycopg2 fallback required.
- safe-db-write allowlist expansion prompts must specify allowed columns per table: when a FIX/CONFIG prompt adds new tables to the Safe DB Write UPDATE allowlist, list the allowed columns explicitly for each table. Column selection is underdetermined without this -- CC must infer from schema + use case context, which requires a schema query step and produces unverified results. Either: (a) list columns explicitly: `aos_intel_analysis: [action_status, action_required, action_items]`, or (b) say "infer allowed columns from schema + use case context -- COO will validate" if judgment-call inference is acceptable for this task. Never leave column selection implicit without acknowledging the gap.: Fix B columns inferred correctly but COO validation flag required.
- Node operation mode before writing fix spec: when a FIX targets SQL inside a specific node, GET the live workflow and verify the node's `operation` field before writing the bug description. n8n Postgres nodes have two modes: `executeQuery` (raw SQL, editable via `query` field) and `insert`/`update` (column-mapping mode, no raw SQL). If the node has been refactored from executeQuery to insert mode, the SQL no longer exists there -- the value likely originates in an upstream Code node fallback expression. Prompt BUG section must specify: "In [Node Name] (`operation: executeQuery`), SQL field `query` contains `{pattern}` -- change to `{fix}`." Never write a node fix spec from memory without verifying the live node's operation type.: Insert node had been refactored to column-mapping; actual source was upstream Code node `|| 'aos'` fallback..
- Constraint violation error message: when describing a CHECK constraint bug, use the exact constraint name from the execution error message (e.g., `expenses_category_check`) -- not a prose description of which column triggered it. Constraint names are authoritative; prose descriptions can be wrong.: prompt said "business_id CHECK constraint violated" but actual error was `expenses_category_check` (category='test' not in allowed list).
- Symptom LAST VERIFIED date: when describing a bug symptom, append "LAST VERIFIED: [date]" to the Symptom line. Bugs fixed between prompt authoring and CC execution waste diagnostic time and can confuse diagnosis.: Bug B1 (ExpressionError) described as current but had been fixed in a prior session -- 15 minutes spent confirming no action needed..
- Verify current state before prescribing fixes: the live workflow may already have one of the suspected bugs fixed. For FIX prompts targeting multiple bugs, add a "verify current state first" gate: before applying any fix, CC should GET the live workflow via REST API and confirm the bug pattern still exists at the suspected location. Step the prompt as: "Step N: Verify [bug X] still present in [node] — if already fixed, document and skip." This prevents redundant PUTs and avoids masking which fix addressed which symptom.: Error A was already fixed in the live workflow; prompt spec assumed both bugs were unfixed.
- Node count verification: before writing a FIX prompt for any workflow, GET the live workflow and embed the verified node count in the CONTEXT block as "VERIFIED NODE COUNT: {n}" and use it in the DoD ("workflow has {n+added} nodes after fix"). Never estimate or carry over node counts from memory -- n8n workflows gain nodes over time and the count in a README or prior prompt may be stale.: prompt said 22 nodes (DoD said 23); live GET showed 24 nodes (final = 25) -- a 2-node discrepancy that would have caused verification confusion.
- Node existence check for "+N nodes" specs: when specifying nodes to add, GET the live workflow and verify each proposed node does NOT already exist by name. List each as "ADDED (net-new)" or "UPDATED IN PLACE (already exists).".: prompt said "+2 nodes per workflow" but both already had "Prepare HC Data" from a prior session -- actual delta was +1. Specifying ADDED vs UPDATED IN PLACE eliminates confusion about expected post-fix counts.
- Code node JavaScript in specs: when writing Code node JS in the prompt SPEC or BUG sections, always use `$input.all`, never `$input.first`. This applies to JS you write IN the prompt, not just to CC-generated code. applies here -- CC will override `$input.first` to `$input.all` per convention, but the discrepancy causes confusion and requires build log documentation.: prompt Prepare HC Data spec used `$input.first`; CC overrode per rule.
- Fan-out connections from Code nodes: when a Code node (e.g., Prepare HC Data) connects to multiple downstream nodes, document ALL outgoing connections and for each downstream node note whether it depends on the Code node's OUTPUT or reads from another source. Example: "Prepare HC Data -> Success: Log (reads raw_result_safe from Code output) AND Success Response (reads from `$('Insert into Postgres')` directly -- NOT dependent on Code output, no rewiring needed)." Without this, CC must investigate dependencies before touching the Code node.: W12 Prepare HC Data fanned to both Success: Log and Success Response -- took 5 min to verify Success Response didn't need rewiring.
- Switch typeValidation routing bugs: when describing a routing bug where all commands hit a fallback/catch-all path, include `typeValidation` as a top-ranked suspect (above expression value bugs and connection bugs). The symptom -- ALL named outputs have 0 items, fallback fires for every item -- is a near-certain signature of `typeValidation: "strict"` on expression leftValues. In the SUSPECTED CAUSES section, list it first: "Check `typeValidation` on all Switch conditions (`parameters.rules.values[*].conditions.options.typeValidation`). If `'strict'`, change to `'loose'` on all conditions." N8N-API-REFERENCE pitfall #28.: typeValidation strict was listed last of 4 suspects; was the actual cause.
- Name version bump steps: before writing a "bump name to Vx" step in a FIX prompt, GET the live workflow and verify the current name. Write the step as conditional: "Bump n8n name to V2 IF current name is still V1" -- not prescriptive..: step said "bump to V2" but live workflow was already V2 (fixed in a prior session). No harm, but wasted spec effort and required a no-op note in the build log.
- Test UUID format in verification specs: all UUID segments must use valid hexadecimal characters [0-9a-f] only. The segment "test" contains 't' and 's' which are not hex digits -- Postgres rejects this at UUID type cast before reaching any intended constraint or row data, making the test exercise the wrong failure mode. Use well-formed test UUIDs like `00000000-0000-0000-0000-000000000001` or `aaaaaaaa-0000-0000-0000-000000000001`.: prompt spec used `aaaaaaaa-test-0000-0000-000000000002`; test 2 (valid INSERT) failed with DB error instead of succeeding.
- Email Router classifier fix prompts: always include the valid category list in IMPORTANT NOTES. Valid categories: `action | financial | legal | platform | vendor | quarantine`. The prompt that produced Bug C proposed category "review" and label "MRMINOR/Review" -- neither exists in the Router. CC used `vendor` as closest match. Without the valid list, CC must guess and may silently use a wrong category.
- Test payload `business_id` session number: when a FIX prompt includes a test payload with `business_id: "test-{workflow}-s{N}"`, use `{SESSION}` as a placeholder or instruct the COO to update to the current session number before handing off. Stale session numbers in test payloads have no functional impact (the field is checked for duplicate prevention only when `force: false`), but they cause confusion in build logs and make it harder to trace which test run belongs to which session.: prompt used `s549` in `business_id`; CC updated to `s553`. Recommendation: `"business_id": "test-wikifier-v2-{SESSION}"` with a note "replace {SESSION} with current session number."
- Test payload must match live Normalize Input required fields: before writing a webhook test payload in any FIX or BUILD prompt, GET the live workflow and inspect the `Normalize Input` (or equivalent input-validation Code node) required fields list. Add every required field to the payload or document its default. A test payload missing a required field fails at the wrong layer -- the spec's "known bad behavior" is never reached, the test proves nothing, and pre-fix baseline is unrecordable..: spec payload omitted `page_registry_path` (required by Normalize Input but not used downstream), causing pre-fix test to fail at Normalize Input instead of reaching the Validate node.
- Status CHECK constraint before E2E: for any FIX+E2E task where the workflow UPDATEs a `status` column, include a CONTEXT QUERIES step to verify the target value is in the live CHECK constraint BEFORE triggering the E2E test. Query: `SELECT pg_get_constraintdef(oid) FROM pg_constraint WHERE conname LIKE '%{table}%status%'`. The pre-prompt verification of column existence is NOT sufficient — the column can exist but the target value (`'approved'`, `'published'`, etc.) may be absent from the CHECK enum.: `agency_blog_topic_queue.status` column existed; E2E failed mid-execution because `'approved'` was not in the constraint. Required mid-task DDL fix. See the anti-pattern log (general CHECK constraint gate).
- Slack node expression fixes: use plain field names for display (e.g., `workflow_name`), NOT `_safe` variants (e.g., `workflow_name_safe`). The `_safe` suffix is the pgEscape output for SQL nodes only -- in Slack text display, `_safe` values contain escaped apostrophes (`''`) that appear as double-apostrophes to the reader. Rule: plain variants for display (Slack, Set), `_safe` for SQL `'{{ }}'` parameters only. Bug B: prompt IMPORTANT NOTE suggested `_safe` for Slack; correct behavior was plain (matching current template).
- Multi-target GET-all-before-any-PUT: When a FIX or CONFIG-EDIT targets the same field/value across N workflows, instruct CC to GET all N workflows first and verify the current field value before writing ANY PUT. Build a fix list — only workflows where current value ≠ target value proceed to PUT.: BLG-02/03/04/06a/09 already had mode:id; only BLG-08 needed the channel change. 5 unnecessary PUTs avoided. Instruction: add a “Pre-write verification” step in §4 TASK or §8 IMPORTANT NOTES: “GET all target workflows. For each, confirm [field] current value. Fix list = workflows where current ≠ target. Do NOT PUT any workflow not on the fix list.” Distinct from (stale prompt facts) — that gate runs at prompt-write time; this runs at CC execution time.
- Execution limit as first diagnostic step for webhook empty-body: When a FIX task targets a webhook returning HTTP 200 with empty body, add “n8n execution limit exhausted” as item (d) in SUSPECTED CAUSES — especially if the symptom appeared suddenly and ALL workflows are affected simultaneously. Diagnosis: `GET /api/v1/executions?limit=5` — check error field for “Execution limit reached”. If confirmed: no code fix will help; Jordan must upgrade the plan at app.n8n.cloud or wait for monthly billing reset. Webhook `responseMode: responseNode` returns empty 200 because the billing wall kills the execution before `Respond to Webhook` fires. Mitigation: deactivate high-frequency schedule workflows (every 5 min or less) immediately — 60-sec schedules burn ~120 executions/hr even while failing. n8n GET /workflows paginates at 50 — always use nextCursor pagination when searching for a workflow (Pitfall #47; the target may be on page 2+).
- `availableInMCP` PUT body — OMIT, not include (FIX-INTAKE-KEY-REFRESH): Per N8N-API-REFERENCE `availableInMCP` should be OMITTED from the PUT settings dict. Some COO prompt §8 notes say "keep `settings.availableInMCP: true` in PUT body" — follow N8N-API-REFERENCE instead. n8n preserves the MCP toggle without the field in PUT; including it causes HTTP 400 on some workflows. Conservative 6-field set (`executionOrder`, `callerPolicy`, `saveDataErrorExecution`, `saveDataSuccessExecution`, `saveManualExecutions`, `saveExecutionProgress`) is safe. Post-PUT GET confirmed `availableInMCP: True` preserved by n8n without the field being sent.: CC correctly omitted it despite prompt §8 note saying to include it.
- versionId prefix vs full UUID in access checks: n8n REST API always returns the full 36-char UUID (e.g., `"877bb73a-6c28-4e85-b235-7b7c10046138"`), not the 8-char prefix abbreviated in COO prompt CONTEXT blocks. CC access check scripts must use `startswith` not `==`: `assert wf["versionId"].startswith("877bb73a"), f"versionId mismatch: {wf['versionId']}"`. COO ACCESS CHECK bullets should say "confirm versionId **starts with** `{prefix}`" not "confirm versionId = `{prefix}`".
- JSON global replace with embedded JavaScript newline ( confirmation): when the NEW string in a `json.dumps(wf).replace(OLD, NEW)` operation contains a JavaScript line break (e.g., inserting a `const` before an existing line), use Python `\\n` (literal two-char backslash+n = valid JSON escape), NOT `\n` (Python chr(10) = invalid control character inside a JSON string). `\n` in the replacement causes `json.loads(replaced)` to raise `JSONDecodeError: Invalid control character`. Pattern: `NEW = f"const ipSalt = '{salt}';\\nconst ipHash =..."`. named this in for SQL confirms the same applies to jsCode.
- Merge v3.2 runtime compaction + position-independent reads: when a branch upstream of Merge emits 0 items, n8n skips that Format/Code node and Merge produces fewer outputs than expected — all absolute-index reads (`$input.all[N]`, `allInputs[N]`) after Merge silently mis-assign. Fix: read each branch from its source node by name using `$('NodeName').first` in a try/catch (returns `{}` if unexecuted). Also remove any `if (allEmpty)` compact-layout guard — it unconditionally hides sections on quiet days independent of the index bug. Both bugs coexist in the same Code node and require the same PUT. Root: Format: Silence Reminders + Pipeline Health skipped on quiet days; Merge compacted 10→8; allInputs[7]=Wiki Lint (not silence), allInputs[8-9]=undefined. Silent at execution time. Diagnostic: inspect Merge output item count in execution debug.
- Merge node `numberInputs` invariant — silent default fallback: when a digest or report section silently shows a default/fallback string despite the branch being wired, check `Merge.parameters.numberInputs` vs max connected index. Invariant: if any branch wired to Merge input index N, `numberInputs` must be >= N+1. n8n does not validate this at PUT or execution time — miscount is silent, no execution error, no health check alarm. Diagnostic: GET workflow, enumerate connections INTO Merge (find all entries where target `node == “Merge”`), find `max(index)`, compare to `Merge.parameters.numberInputs`. Fix: global JSON replace `”numberInputs”:{old}` → `”numberInputs”:{new}` (applies — catches both `nodes` and `activeVersion.nodes`). **BUILD DoD gate:** any prompt adding a new Merge branch must include: “Verify `Merge.parameters.numberInputs` >= max_connected_index + 1 after PUT.”

- REPRODUCE-FIRST bulk cluster must have pre-existing dispositions (FIX-INTEL-DISPOSITION-ADOPT): when selecting a bulk idempotent test cluster via `GROUP BY cluster_id HAVING count(*) >= 2`, rows with NULL dispositions are not idempotent test targets — the first PUT will write a new value and the test cannot confirm idempotency. Add `AND disposition IS NOT NULL` to the HAVING clause (or use WHERE before GROUP BY). Example fix: `SELECT cluster_id, disposition, count(*) FROM intel_analysis WHERE disposition IS NOT NULL GROUP BY cluster_id, disposition HAVING count(*) >= 2 ORDER BY count(*) DESC LIMIT 1`. Applies to any FIX prompt with a bulk idempotent smoke test step.

- ACCESS CHECK STOP condition: versionId change ≠ wrong workflow (FIX-INTEL-WEEKLY-REPORT-OBSERVABILITY): The pattern "if name/version differ → STOP" conflates two distinct signals. **Name mismatch** = wrong workflow (genuine STOP). **versionId mismatch** = workflow was modified since the prompt was authored (expected whenever any edit occurred between authoring and execution). The correct runtime decision: (1) if name differs → STOP; (2) if versionId differs but name matches → verify that the listed defect conditions still hold in the live GET; if they hold, document the discrepancy in build log and proceed; if any defect condition already resolved → document + skip that sub-fix, proceed with the rest. Companion to (prefix format) and (stale facts). **COO prompt authoring rule:** ACCESS CHECK STOP bullets should read "if name differs → STOP" and treat versionId as a staleness indicator, not an identity gate. Node count in the prompt (VERIFIED NODE COUNT) should likewise be confirmed from live GET at task-start — a miscount blocks a valid fix.

- Data-pipeline scheduled-vs-manual batch composition gap: For data-pipeline FIX tasks where the workflow processes a queue/batch of items from a DB table, a manual trigger draws from the CURRENT queue (whatever is unprocessed at that moment), which differs from the scheduled run's batch. A manual trigger that succeeds does NOT confirm the scheduled path -- it only confirms the fix works for the current batch. For scheduled intel/digest workflows: add a 'cron confirmation pending' note in the feedback file and flag authoritative pass as contingent on next scheduled run. (N8N-API-REFERENCE Pitfall #13) covers the trigger mechanism difference; this covers the DATA COMPOSITION difference.

- `haios_health_checks` L1 query column is `timestamp` not `checked_at` (FIX-STACK-UPDATE-UUID-CAST): the HC table has `timestamp` and `created_at` as time columns; `checked_at` does not exist. COO FIX prompts that include an L1 verification query like `SELECT state, checked_at FROM haios_health_checks` will fail with "column does not exist." Use `timestamp` instead. Related: covers the broader pattern of HC column mismatches in write paths.

- Merge node removal when losing an input (FIX-DOCGOV-RETIRE-CHECK2): when a Merge node has `parameters: {}` (no explicit `numberInputs`) and one of its upstream inputs is removed, the clean fix is to REMOVE Merge entirely and wire the remaining upstream node → downstream node directly. Attempting to drop `numberInputs` to 1 when `parameters: {}` requires adding the field rather than reducing it — removing Merge is simpler and avoids an orphan port. Diagnostic: GET Merge node params; if `parameters: {}` and only one input remains after removal, delete Merge from `nodes` and rewire connections. (numberInputs invariant) covers the parallel KEEP-Merge case where numberInputs must be bumped up.

- D-cascade FIX prompts must re-read prior-D-task targets (FIX-CC-CONFIG-STALE-REF chain): when a FIX is one dispatch in a multi-task cascade (D1, D2,...) and its correctness depends on a file a PRIOR sibling task claimed to modify, add an explicit CONTEXT QUERY / ACCESS CHECK step to re-read that file at execution time -- do NOT encode the prior task's *claimed* end-state as a prompt assertion.: the D1 stale-ref prompt assumed D2 had stripped a reference from all config files; D2 only touched CLAUDE.md, leaving a live ref in MANIFEST.md -> D1 emitted a false positive, forcing a D1b follow-up. This is (pre-assertion verification) applied ACROSS sibling cascade tasks: a prior task's *intended* edit is not a verified state. Distinct from (stale prompt facts at authoring time) -- this is a stale cross-task assumption about a sibling dispatch's effect. (Originated as a D1b process-feedback recommendation; COO authored it here after verifying CC's reported application to PROMPT-TEMPLATE.md had not landed.)

- landscape_summary populated with parse-error string in fallback INSERT (FIX-BEST-PRACTICE-FLOOR-RECALIBRATION): when a Code node has (1) JSON.parse on Claude API output that can fail (fenced JSON), and (2) a fallback INSERT downstream that uses a `landscapeSummary` variable, a parse failure will populate `landscapeSummary` with the full parse-error string BEFORE the fallback branch executes. The fallback INSERT correctly fires and writes a best_practice row (class/confidence/action_status all correct), but `landscape_summary` in the DB contains a raw error string rather than a human-readable summary. Fix: add fence-stripping (pattern) to the JSON extraction before the landscapeSummary assignment in any Parse Response Code node that has a downstream fallback INSERT. For FIX prompts targeting intel analysis workflows: add "verify landscape_summary is human-readable (not 'Parse error...') in the inserted row" as a DoD line.

- "BOTH paths" DoD requires signal availability specification: when a Part 4 / close-out DoD says "confirm best_practice via BOTH paths: floor path AND merit path", the prompt MUST specify what to do if only one type of signals (floored OR non-floored) is available at trigger time. Without this, CC completes the floor path and marks merit path as DEFERRED with no clear COO follow-up action. Pattern: add a fallback note to the DoD: "If no non-floored signals are available for the merit-path check, document as DEFERRED and include a follow-up query to run against the next scheduled production execution."

- `stop_reason: max_tokens` is the primary diagnostic signal for Claude API parse failures (FIX-PARSE-RESPONSE-FENCE-STRIP): when a FIX prompt suspects a parse/fence-strip bug, the first access-check step must inspect the Claude API node's execution output for `stop_reason`. If `stop_reason: max_tokens` → the bug is truncation (fix: increase max_tokens); investigate parse logic ONLY when `stop_reason: end_turn`.: task mis-diagnosed as missing fence-strip; the fence-strip was already present; actual cause was `max_tokens: 256` truncating the synthesis response. Two wasted script attempts before stop_reason was checked. **FIX prompt template addition:** in §CONTEXT QUERIES add a step "inspect Claude API node execution output — note `stop_reason` and `output_tokens`." If stop_reason=max_tokens, the bug description and fix in the prompt will be wrong — COO must rewrite before dispatching. (updated).
