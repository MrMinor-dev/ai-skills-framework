# AUDIT Task Type

Review, check, verify.

**Recommended effort:** `xhigh`

Class default — discovery + evaluation + synthesis. High-signal reasoning task. Not typically lowered.

<!-- COO uses this file when writing a CC prompt for a AUDIT task. Copy the spec block below into the prompt's §7 TASK-TYPE section, then embed relevant session-learning notes in §8 IMPORTANT NOTES. -->

## Spec Block

```markdown
## AUDIT SCOPE
{What to audit. File paths, workflow IDs, repo.}

## CHECKLIST
{Scoring criteria. Point values per category.}

## OUTPUT FRAMING
- **Audience:** {who reads this — Jordan / team}
- **Decision:** {what decision this informs — remediation priorities / sign-off / go-no-go}
- **Format:** {markdown doc / table / summary + per-item findings}
- **Length:** {target word count or page count}
- **File path:** {where to write audit report}
```

## Session Learnings

**Architecture / doc audit notes:**
- **Parallel agent pattern (10+ files):** Launch 2 Explore agents in parallel (each reading ~6-8 files). Cuts read time roughly in half vs. sequential. State this in CC ACCESS CHECK section. Default for AUDIT tasks with 10+ files.
- **Subagent dispatch + Drive path handling:** Two distinct failure modes when Explore subagents read Drive files — treat differently. (a) Drive locally mounted but subagents don't know: add to EACH subagent prompt top: "IMPORTANT: All files below are on the LOCAL Windows filesystem. Google Drive is mounted locally. Use the Read tool directly — do NOT attempt any MCP authentication." Without this, 1 in 2 subagents may request MCP auth for `` paths non-deterministically (Phase 4: 3 of 6 affected on first dispatch; retry with explicit instruction resolved all 3). See Watch W53. (b) Drive not locally mounted (rare — MCP auth genuinely unavailable): fall back to main-context reads — no information gap, higher context cost. Fallback is last resort, not a substitute for fixing the subagent prompt. Pre-stage Drive content locally or pass file contents directly to subagents if context budget is tight.
- **File content reads for ambiguous filenames (filesystem/Drive audits):** For audit tasks that specify "metadata only," still grant CC explicit permission to read file contents when the filename alone is insufficient to determine purpose or correct location. Without this, CC will pause for a Plan Mode amendment. Add to IMPORTANT NOTES: "CC may read file contents when the filename alone is insufficient to determine purpose -- prioritize hash/generic names, apparent misplacements, type/folder mismatches. Read just enough to determine purpose." Priority targets: hash-named files (e.g., `remixed-a9c7c0b7.md`), files with HTML/code-syntax names (e.g., `DOCTYPE html Pathway.docx`), files whose extension doesn't match folder context.
- **Non-scope exclusions:** When the audit directory contains session artifacts (CC-PROMPT-*.md, CC-BUILD-LOG-*.md, CC-FEEDBACK-*.md), add an explicit exclusion line in IMPORTANT NOTES: "Ignore files matching CC-PROMPT-*.md, CC-FEEDBACK-*.md, CC-BUILD-LOG-*.md in this directory." Prevents false scope confusion. See the anti-pattern log.
- **Secondary scan glob exclusions:** When specifying `*DESIGN*.md` or `*SPEC*.md` glob patterns for secondary scans, add an explicit exclusion for CC session artifacts: "Exclude CC-PROMPT-*, CC-BUILD-LOG-*, CC-FEEDBACK-* from the scan." These filenames contain DESIGN or SPEC and will match the glob. If not excluded, CC correctly flags them as "CC artifacts, no audit action" but they appear in the scan output and require a judgment call that wastes a step.
- **Staleness threshold:** Add a "Staleness threshold" parameter (e.g., "Flag docs not updated in more than a few sessions for freshness review") to remove the CC judgment call on what counts as stale.
- **Path-scoped rule handling (orphaned-rule criterion):** Rules in `~/.claude/rules/` with `globs:` frontmatter auto-load for their target scope and count as "referenced" -- do NOT flag as orphaned. Only flag rules with no `globs:` frontmatter that are also not cited in CLAUDE.md or any active prompt. Add to IMPORTANT NOTES if the audit scope includes `~/.claude/rules/`: "Path-scoped rules (frontmatter `globs:`) count as referenced even if not listed in CLAUDE.md."
- **Rule attribution verification:** If the prompt attributes a ≤N count limit, naming convention, or other specific rule to a `~/.claude/rules/` file, CC must verify the rules file actually states that rule before including it in the report. A rule described only in DOC-AUDIT-PLAN.md or CLAUDE.md is not the same as a rule in the rules file — attribution errors create confusion for Ph8-Ex. Add to AUDIT SCOPE: "Verify all rule attributions against the actual rules files before reporting." (Note: n8n-rollback.md attributed as source of ≤3 snapshot limit; actual source is DOC-AUDIT-PLAN.md §8. n8n-rollback.md has no count limit stated.)
- **Priority ordering for large file groups (5+ files):** When the audit scope includes 5+ files in a single directory or group, add an explicit read priority order in the prompt: "If context-limited, read in this order: [file 1, file 2, ...]. Strategic/decision docs before spec/detail docs." Compaction will drop the tail of any read-heavy task. Without ordering, tail files are random rather than the lowest-value ones. Add as a field under AUDIT SCOPE or IMPORTANT NOTES. See the anti-pattern log.
- **Supplementary spec/reference files in domain directories:** When a domain directory contains files that are reference/spec docs rather than domain definitions (e.g., `N8N-NODE-CONFIGS.md`, `HEALTH-CHECK-PATTERNS.md`, `*-SPEC.md` in Infra/), the prompt must explicitly state whether these files are: (a) in scope for domain-doc audit criteria, or (b) forwarded to a later knowledge/reference audit phase. Without this, CC must make a judgment call mid-session that may not match COO intent and requires a build log note. Recommended phrasing: "Apply domain-doc criteria only to `*-DOMAIN.md` files. Treat `*-NODE-CONFIGS.md`, `*-PATTERNS.md`, `*-SPEC.md`, `*-STRATEGY.md` as reference docs -- note their presence but forward to Phase 7 scope.": 5 supplementary spec files in Infra/ forwarded to Ph7 by CC judgment.
- **Prose-path scan (xref audits):** Markdown-link grep catches only a fraction of cross-references in this tree. Most references are prose paths in backtick wrappers (e.g., `HAIOS/Architecture/BUILD-ROADMAP.md`). For a complete xref scan, specify two operations separately: (a) markdown link scan (`\[.*?\]\(([^)]+)\)`) and (b) prose path scan (backtick-wrapped paths matching file-like patterns, e.g., `` `[A-Z][A-Z0-9/_-]+\.md` ``).: 383 files, only 81 markdown links found -- prose path references were not checked. Without scan type (b), "zero broken links" is accurate but incomplete.
- **PowerShell date display in subagent Get-ChildItem:** When Explore subagents enumerate files via `Get-ChildItem -Recurse` on Windows Git Bash, the default date format can truncate the year (e.g., showing `04/01/2015` when the actual year is 2026) or display inconsistently across columns. For any AUDIT prompt that relies on modified-time data from subagents: add to the subagent prompt "Use `Get-ChildItem -Recurse | Select-Object FullName,Length,LastWriteTime | Format-Table -AutoSize` to ensure consistent timestamp output." Cross-reference against file sizes when a timestamp looks anomalous — same size + suspicious date = display artifact, not a real drift finding.: `commands/sync-config.md` showed 2015 in canonical subagent output vs. 2026 in mirror; size parity (1,443b both sides) confirmed same content.
- **Broken-ref subagent findings — main-context verification required:** Explore subagents have high false-positive rates on negative-space checks (asserting a path does or does not exist). 4 of 18 raw subagent S1 findings in Phase 3 staleness audit were false positives; all caught by main-context Glob/Grep. Add an explicit "false-positive filter" step to every AUDIT prompt that dispatches subagents for broken-ref scanning: "After subagents return, re-verify all S1 broken-ref findings via main-context Glob or Grep before including in final report." Watch W52 tracks recurrence. See the anti-pattern log for related subagent verification pattern.

**Doc compliance audit notes:**
- **Pre-known findings fast-verify (W54):** If the prompt lists pre-known findings with specific field names or values, CC should re-read the target file at execution start and confirm the field name/value matches the claim before building the audit pass on it. COO: derive pre-known findings from the most recent direct file read, not memory or older notes. State findings as "verify that X has field Y with value Z" — not assertions of current state.: `ssot-for: true` vs. actual `ssot: true` — different field name; required mid-pass reclassification. See Watch W54.
- **High-volume Tier 1 batch pattern:** When a mechanical audit pass discovers N≥10 SSOT-Y docs all missing the same frontmatter field, surface as ONE Tier 1 batch finding (not N individual findings). Include (a) sample 3 with proposed values, (b) full list in report appendix, (c) explicit note "once Jordan approves batch, COO executes N mechanical Tier 2 edits.": 19 SSOT-Y docs missing `ssot-for:` — surfaced as single T1-01. Pattern prevents burning Jordan's decision capacity on 19 identical approval prompts.
- **Build log incrementality for long audit passes:** For audit passes running 3+ parallel agent dispatches, write build log entries after EACH agent run returns — not at the end of the full pass. Context compaction mid-audit destroys in-session state; build log is the recovery mechanism. If the build log still reads "[to be filled after agent runs]" at compaction time, the compacted session cannot recover.: compacted mid-pass; build log was started but not populated — recovery required session summary reconstruction. Post-compaction data loss limited to 7 AOS/Agency Check A mismatches (out-of-scope items).

**Workflow README audit notes:**
- **No status field in README:** If a README has no status field at all, do not FLAG:Status -- note as minor gap in the per-workflow row and score CLEAN unless other flags apply. Do not infer status from adjacent context.
- **No n8n name suffix for version comparison:** If a workflow's n8n name has no version suffix (e.g., `HAIOS-Infra-Remediation-Cleanup [L2]` with no V1/V2), version comparison is not possible -- note as "unverifiable" in the row, do not FLAG:Version.
- **FLAG:Promote-Up with existing canonical home:** If the cross-workflow principle already has a primary copy in an existing SSOT (e.g., already in EXTERNAL-DATA-SANITIZATION-SPEC.md), note "primary copy already exists at {path}" in the finding. COO decision: strip redundant copy from README, or leave (especially for archived READMEs).
- **Parallel agents NOT suitable for workflow node absence-check audits:** The "parallel agent pattern" (above) applies to doc/file reading, NOT to n8n workflow node analysis. For audits that check for presence or absence of specific nodes, code patterns (e.g., try/catch implementations, channel IDs, HC write nodes), use main-context analysis only — subagents have high false-positive rates on negative-space findings (Note: 4/18 false positives confirmed). Do NOT include a parallel-agent recommendation in §8 of any workflow audit prompt that involves node or code pattern analysis. If the prompt mixes doc reads (parallel OK) and node analysis (main context required), split into explicit phases with separate method instructions per phase.

**Workflow revalidation / remediation audit notes:**
- `haios_remediation_log` PATCH status values: valid values are `pending`, `in_progress`, `fixed`, `escalated`, `dismissed` — NOT `resolved`. Using `resolved` hits CHECK constraint code 23514. Verify via live DB query before writing any PATCH body. See the anti-pattern log. caught in Plan Mode hit at runtime from a stale prompt example. ** COO confirmation:** COO hit this 3× during direct safe-db-write (attempted `resolved` on 8 rows across 3 attempts before switching to `dismissed`). Applies to COO direct SQL writes, not just CC prompts.
- `aos_expenses` column names: `expense_id` (PK), `recorded_at` (timestamp). Not `id`/`created_at`. Always verify via live DB query (`SELECT column_name FROM information_schema.columns WHERE table_name = '{table}'`) before writing cleanup SQL or REST filters.
- Pending entry counts: never hard-code counts from the spec. Always query fresh at execution time (`SELECT... WHERE status IN ('pending','in_progress')`) — new entries may appear between spec authoring and execution.: spec said 5 entries; 6th appeared during audit day.

**Citation / frequency-scan audit notes (applied):**
- **Never use a "known fact" as BOTH prompt context AND a pass/fail DoD control.** that session's AP-citation-scan prompt asserted *"#108 has zero rows"* as trusted-as-given context, then made "Table D includes #108" a literal DoD checkbox. Live verification found #108 **does** have a row — so the control failed for a legitimate reason (the premise was stale), and the report had to spend a section explaining that a red X was actually a green check. A control built on a premise cannot distinguish *"the scan is broken"* from *"the premise was wrong"* — it conflates them, and the reader must reverse-engineer which. **Phrase such controls conditionally:** "Table D includes #108 IF #108 is still zero-row at execution time; otherwise report the discrepancy in a dedicated section." Better still: derive the control from live state at execution rather than from the prompt's belief. Same family as — a prompt's "known fact" is a claim with a timestamp on it.
- **Anchor the left edge of short all-caps citation greps with `\b`.** A pattern like `AP[ -]#?(\d{1,3}[ab]?)` false-matches inside `GAP-1`, `CAP 500`, `ROADMAP 4.20` — 39 of 44 raw variant hits (89%) at that time. See.

**n8n workflow credential-exposure audit notes:**
- **Don't assume workflow GET strips credentials — verify empirically first.** `N8N-API-REFERENCE.md`'s note says stripping is "not universal" and gives a safe-always-inject rule for PUT, but doesn't tell CC which to expect on a read-only credential-audit GET. (28-workflow MCP-agent security audit): every node's `credentials` field came back fully populated (id + name) across `postgres`, `httpHeaderAuth`, `anthropicApi`, `gmailOAuth2`, `slackOAuth2Api`, `googleDriveOAuth2Api` types — none stripped. This was materially better data than the prompt's planned CREDENTIAL-MAP.md cross-reference method (CREDENTIAL-MAP can drift; live GET can't). For any future audit needing per-node credential attribution: do one live GET first and check whether `credentials` is populated before committing to a cross-reference-only method.
- **Skipping subagent delegation entirely was correct for judgment-heavy security audits.** Where the audit's core question requires node-level flow tracing (does output X feed write Y with no gate?) across the full node set, per-workflow subagent summarization (even the standard 2-Explore-agent pattern from that session) reintroduces the exact false-positive risk the prompt is trying to avoid. did all 28 workflows' fetch as a deterministic script (no LLM judgment in the fetch step) and all classification/tracing in main context — found one credential-exposure finding (misattached `httpHeaderAuth` credential sending a CRITICAL-blast-radius key to an external endpoint) that a per-workflow subagent summary pass would likely have missed, since it required cross-referencing the node's credential object against its actual destination URL, not just noting "has a credential."
- **Never per-file-loop a bulk grep over `the shared drive`.** A `while read` loop over 710 Drive-mounted files hit the 3-min Bash timeout with zero output; one `grep -r` did the same scope in under a minute. See.
- **The absence findings are the dangerous ones.** Any "X has no row / no hits / not found" result from a scan must be re-verified against the specific instance before it is acted on OR recorded — a false absence turns remediation into damage (Note: a phantom " is missing" nearly caused a duplicate row on the system's most safety-critical AP). See.
